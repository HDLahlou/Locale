Task M1-1: Build the account service: accounts, emailed sign-in codes through a pluggable sender, credential issue and refresh, display-name change, and the host-link email.

Sections: python3 -I docs/agentic/tools/digest_section.py top 1 2 4.1 5.5 5.8 6 8 12

Context: `apps/service` is an empty binary crate named `service`. `crates/proto` has the request and response types for the five endpoints (`proto::service`, see `crates/proto/CONTRACT.md`), and the credential library (`proto::credential`, task M1-2, merged): `sign_credential`, key generation, the development key list. Use them; define no wire type of your own. The service is one small process with SQLite, deployed later by a person (one Fly.io machine, EU). It must never accept or store event or photo data (success criterion SC7): this is checked by a test over its route table. The production signing key and the Postmark API key are supplied by a person through environment variables at deploy time; you only ever use a development key and the console sender, and nothing in tests sends email or leaves loopback.

Files in scope: `apps/service/**`, the `[workspace.dependencies]` table of the root `Cargo.toml` (alphabetical) and `Cargo.lock`. Touch nothing else. If a file outside scope must change, stop and say so.

Acceptance criteria (all must hold):
- A library target inside `apps/service` (so tests and the future harness can start the service in-process on a loopback port) plus the thin `service` binary. Configuration from environment variables with safe development defaults: listen address, database path, signing key and its `kid`, sender choice (`console` or `postmark`), Postmark token and From address, desktop download URL (configurable, per digest C14). Starting with the `postmark` sender but no token, or in a production mode with the development signing key, fails at startup with a clear message.
- SQLite schema per digest §6: `account(id, display_name, email, created_at)`, `login_code(email, code_hash, expires_at, attempts)`, `refresh_token(hash, account_id, device_pubkey, expires_at)`; migrations as in a normal service; codes and refresh tokens stored only as hashes; email compared case-insensitively.
- `POST /v1/auth/start {email}` → 204 always (no account enumeration), creates a 6-digit code valid 10 minutes, sends it through the sender trait. Rate limits per email and per IP (choose values; list them).
- `POST /v1/auth/verify {email, code, display_name?, device_pubkey}` → `{account, credential, refresh_token}`. Creates the account on first sign-in (a display name is required then). Wrong code increments attempts; after 5 wrong tries the code is locked and a correct code is refused; an expired code is refused; a used code cannot be reused. Code comparison is constant-time.
- `POST /v1/credential/refresh {refresh_token, device_pubkey}` → `{credential}`: only for an unexpired token bound to that device key; a mismatched device key is refused. Decide and state the refresh-token lifetime and whether it rotates.
- `PATCH /v1/account {display_name}` → `{account, credential}` and `POST /v1/host-link` → 204 (emails the configured download link to the account's address), both authenticated with `Authorization: Bearer <refresh_token>` as the contract says.
- Credentials are signed with `proto::credential`, life 7 days, role `verified`, carrying the device public key; a test verifies an issued credential with `verify_credential` against the matching public key list.
- A sender trait with a console sender (logs "code sent" without the code in production mode; exposes the code to tests through an in-memory recording sender) and a Postmark sender that builds the correct HTTPS request; the Postmark sender is tested only against a fake server on loopback, never the real API.
- Errors use the contract's error body. Display names are length-limited and trimmed. Request bodies are size-limited. Logs never contain codes, tokens, credentials or full email addresses.
- SC7 test: enumerate the router's routes and assert the set is exactly the five paths above (plus a health check if you add one); assert no handler accepts a multipart or binary body and that an oversized body is rejected.
- Time comes from an injectable clock so expiry and lock tests do not sleep.
- Tests for every criterion are added and pass, all in-process on loopback.
- No interface in crates/proto changes. If a needed type is missing from `proto`, stop and say which.

Verification: run `cargo test -p service` and `just check`; both must pass before you reply. Pipe long output through `tail -40`.
