Context: `crates/proto` is the interface contract (task S3, merged). Its `service` module already defines `CredentialPayload`, `Credential` (`encode`/`decode` of the `v1.<payload>.<signature>` text, without checking the signature), `DevicePublicKey`, `Signature`, `JoinProof`, `proof_message()` and `PROOF_WINDOW_MS`; read `crates/proto/CONTRACT.md` and `crates/proto/src/service.rs` first and build on those types without changing their wire form. The bytes are fixed: the credential signature covers the ASCII bytes `v1.<payload segment>`; the proof signs `proof_message()` (tag, event ID, raw 32-byte fingerprint, timestamp as 8 big-endian bytes of Unix milliseconds). Acceptance criteria (all must hold):
- Signing (used by the service): `sign_credential(payload, signing_key) -> Credential`, Ed25519, over exactly the bytes named above. Key generation helpers for a service key (with its `kid`) and a device key, taking a caller-supplied random source so tests are deterministic.
- A key list type holding service public keys by `kid`, constructible from static data (the host app compiles the list in), with a clearly named development key list for tests and local runs that is separate from any production list.
- Verifying (used by the host, offline): `verify_credential(text, key_list, now_ms)` returns the verified payload or a typed error that distinguishes: malformed text, unknown `kid`, bad signature, expired (`expires_at <= now`), not yet valid (issued more than 5 minutes in the future), wrong role. Verification uses strict Ed25519 verification (rejects non-canonical signatures and small-order keys).
- Proof of possession: `sign_join_proof(device_key, event_id, fingerprint, timestamp_ms) -> JoinProof` and `verify_join_proof(payload, proof, event_id, fingerprint, now_ms)`, which checks the signature against the credential's `device_pubkey` and that the timestamp is within ±5 minutes of `now` inclusive, with typed errors for bad signature, stale and future timestamps.
- One function for the host's decision, `evaluate_identity(credential_text, proof, key_list, event_id, fingerprint, now_ms)`, returning either a verified identity (account ID, display name, device key) or "treat as guest" with the reason. Per digest §4.3 step 4(a) and §8 item 3, every failure means guest, never a rejected join; the reason is for the event log and telemetry only.
- Tests: a valid credential and proof pass; each of these is treated as guest with the right reason: expired, signed by a key not in the list, unknown `kid`, payload altered after signing (any single field), signature altered, credential re-encoded with different JSON spacing or field order, proof signed by a different device key, proof for a different event ID, proof for a different fingerprint, proof timestamp 5 minutes and 1 millisecond old and the same amount in the future (rejected), exactly 5 minutes (accepted), missing proof. A known-answer test pins one credential and one proof, produced from fixed keys written in the test, as literal strings, so any change to the signed bytes fails.
- Secret keys are zeroed on drop where the crate supports it, have no `Debug` output that prints key bytes, and are never serialised by serde.
- No `unsafe`; no async, HTTP, TLS or database crate; exactly one new dependency family for Ed25519 (for example `ed25519-dalek`), with default features trimmed to what is used. Say in your notes what it adds to the dependency tree.
- Tests for every criterion are added and pass.
- No existing interface in crates/proto changes; the staleness test for the generated contract still passes.
