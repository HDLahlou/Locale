### What was built (`crates/image-worker`)

- `src/sniff.rs` — pure Rust. JPEG `FF D8 FF`, PNG signature, ISO-BMFF with `ftyp` first and an HEVC image brand (`heic heix heim heis hevc hevx hevm hevs`) as major or compatible brand. `mif1`/`msf1` alone are refused (AVIF uses them too). One `ImageFormat::Heic` covers HEIC and HEVC-coded HEIF.
- `src/structure.rs` — pure Rust container completeness check, run before ImageIO: a JPEG must reach EOI after a frame and a scan (data after EOI allowed, for Ultra HDR); a PNG must be an `IHDR`…`IEND` chunk chain with valid CRCs and at least one `IDAT`. **Why:** ImageIO decodes truncated JPEG and PNG without any error or incomplete status (it fills the missing rows), so `truncated.jpg`/`.png` passed until this check existed. ImageIO refuses truncated HEIC by itself.
- `src/codec.rs` — `ImageCodec` trait: `decode` (full decode check, returns `Facts { width, height, format, orientation, has_hdr_gain_map }`), `preview`, `compatible`; both return `Encoded { bytes, width, height, facts }` so the decode check runs once per job. `Unsupported` back end returns `CodecError::UnsupportedPlatform`; `platform_codec()` picks it on non-macOS.
- `src/macos.rs` — the only module with `#[allow(unsafe_code)]` (on `mod macos;` in `lib.rs`); each `unsafe` block has a `// SAFETY:` comment. Uses `objc2-image-io`, `objc2-core-graphics`, `objc2-core-foundation`, `libc`. Decode: sniff → structure check → `CGImageSourceCreateWithData` with a type hint → decoder UTI must match the sniffed format (`public.jpeg`, `public.png`, `public.heic`/`public.heif`) → status complete → properties (pixel size, orientation 1-8) → `CreateImageAtIndex` with `ShouldCacheImmediately` → pixel data copied (forces decode) → size and status rechecked. Gain map: `kCGImageAuxiliaryDataTypeHDRGainMap` or the ISO gain map key (built from its string value, because the symbol only exists from macOS 15 and would stop the binary loading on 13/14). Preview: `CreateThumbnailAtIndex` with `FromImageAlways`, `WithTransform`, max size `min(1024, long edge)`, JPEG q 0.80, no metadata. Compatible: full image, JPEG q 0.92; the CGImage colour space is embedded as the ICC profile.
- `src/job.rs` — wire format. `src/child.rs` — what the binary runs. `src/main.rs` — 3 lines.
- `src/worker.rs` — parent API `Worker`.

### Worker protocol

- Parent spawns `exe` (absolute path required, `WorkerError::WorkerPathNotAbsolute` otherwise; never searches `PATH`; tests use `env!("CARGO_BIN_EXE_image-worker")`) with `env_clear()`, cwd `/`, stdin = the already-open input `File`, stdout piped (read up to 64 KiB), stderr null, and one argument: the job JSON, e.g. `{"kind":"preview","claimed":"heic","output":"<parent temp path>"}`.
- The output path is a temp file (`.image-worker-*.partial`) the parent creates next to the caller's destination; the child opens it write+truncate without create; the parent renames it to the destination only on success. On any failure the temp file is dropped (deleted).
- Child reads at most 50 MB + 1 byte from stdin, refuses more, checks content against `claimed` (sniff), runs the codec, writes output, prints one JSON line, exits 0.
- Parent polls every 10 ms: exit, time limit (default 10 s, `with_timeout`), memory (default 1 GiB, `with_memory_limit`). On overrun: kill + wait (always reaped). Non-zero exit, signal, timeout, memory kill, malformed/extra/missing result line, and every codec refusal map to `WorkerError::InvalidImage(InvalidImage { format, size_bucket })`. Other variants: `UnsupportedPlatform`, `WorkerPathNotAbsolute`, `Io(ErrorKind)` (host-side faults: input open, temp create, spawn, rename). No variant carries a path; `Worker`'s `Debug` omits the exe path.

### Memory limit: what is enforced on macOS

- Enforced: the parent reads the child's `ri_phys_footprint` (`proc_pid_rusage`, `RUSAGE_INFO_V2`) every 10 ms and kills the child once it exceeds the limit. Test: a 800 MB allocation under a 200 MB limit is killed well before the timeout; 300 MB under 1 GiB is not.
- Not enforced: there is no kernel hard limit. macOS does not enforce `RLIMIT_AS`/`RLIMIT_DATA` for allocations, so none is set. A child can briefly exceed the limit between two polls (one 10 ms window of allocation). Other OSes: no memory limit yet (Windows job object belongs to M0a-4).

### Defaults I chose

1. Every job carries the uploader's `claimed` format; content that sniffs as another allowed type fails (`FormatMismatch`). This is how `wrong_magic.*` fail the decode check. `InvalidImage.format` is the claimed format (always known; the parent never reads image bytes).
2. Size buckets in MiB (5 MiB, 20 MiB), matching the 52,428,800-byte limit; anything 20 MiB and up is `20-50MB`.
3. `Facts.orientation` is `u8` 1-8, 1 when absent (manifest uses `null`).
4. Compatible copy keeps only the orientation tag (pixels not rotated); no other metadata is copied. Preview has no metadata.
5. One job per process (no pool). The child refuses input over 50 MB without decoding.
6. Output files are created with the temp file's 0600 mode.
7. ImageIO does not read orientation from PNG `eXIf` (gps_exif.png reports 1, manifest says 6); the facts test checks orientation for JPEG only.
