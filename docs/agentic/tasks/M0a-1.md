Acceptance criteria (all must hold):
- `host-core` exposes a listener that binds one TCP port (the requested port, or the next free one if it is taken; port 0 for tests), accepts connections, peeks at the first byte without consuming it, and serves TLS when it is `0x16` and plain HTTP otherwise. Both paths are served by HTTP services passed in by the caller: one for TLS connections and one for plain connections, so later tasks can give browsers a smaller API than apps. The handler can tell which transport a request came in on.
- A function generates the per-event identity: a self-signed ECDSA P-256 certificate valid for a caller-given lifetime, its private key, and the fingerprint (SHA-256 of the certificate DER). The identity can be written to and loaded from a `tls/` directory; the key file is created with owner-only permissions on Unix (mode 0600), and a test checks the mode. A reloaded identity has the same fingerprint.
- `client-core` exposes a pinned-TLS connector (a rustls `ClientConfig` or connector built from a 32-byte fingerprint) that accepts exactly the certificate whose SHA-256 equals the pin, with no CA validation and no hostname check, and still verifies the handshake signature against that certificate. The fingerprint comparison is constant-time. A mismatch surfaces as a distinct typed error that callers can map to `fingerprint_mismatch`.
- Tests, all on loopback: a pinned client completes an HTTPS request to the listener; a client with a different pin fails with the typed mismatch error and the handler is never invoked; a client pinned to the right fingerprint but talking to a listener that presents a different certificate fails the same way; a plain HTTP GET to the same port reaches the plain service; a TLS request never reaches the plain service and a plain request never reaches the TLS service; a connection that sends nothing is closed after a short timeout without blocking other connections; the listener shuts down cleanly on request and frees the port; binding a taken port falls forward to the next free one.
- A slow or stalled first byte from one connection does not delay accepting others (each connection is handled on its own task).
- No `unsafe`. No certificate or key material is logged.
- Tests for every criterion are added and pass.
- No interface in crates/proto changes.
